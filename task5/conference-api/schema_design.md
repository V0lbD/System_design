# Проектирование документной модели MongoDB

## Предметная область

Основные сущности системы:

- пользователи;
- доклады;
- конференции;
- токены авторизации.

В предыдущих лабораторных работах данные хранились в PostgreSQL в нормализованной реляционной модели. Для MongoDB модель проектируется иначе: часть связанных данных встраивается внутрь документов, а независимые сущности хранятся в отдельных коллекциях и связываются через references.

## Список коллекций

Для системы используются следующие коллекции MongoDB:

1. `users` — пользователи системы.
2. `talks` — доклады.
3. `conferences` — конференции.
4. `tokens` — токены авторизации.

## Коллекция `users`

Коллекция `users` хранит пользователей системы: участников, докладчиков и организаторов.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  login: "ivanov",
  password_hash: "hash_123",
  first_name: "Иван",
  last_name: "Иванов",
  role: "speaker",
  email: "ivanov@example.com",
  bio: "Backend-разработчик, интересуется системным дизайном",
  contacts: {
    telegram: "@ivanov",
    github: "ivanov-dev"
  },
  interests: ["backend", "databases", "system design"],
  created_at: ISODate("2026-05-20T10:00:00Z"),
  updated_at: ISODate("2026-05-20T10:00:00Z")
}
```

### Обоснование модели

Пользователь является самостоятельной сущностью, поэтому хранится в отдельной коллекции.

Поля `contacts` и `interests` встроены в документ пользователя, потому что они принадлежат только конкретному пользователю и обычно читаются вместе с ним. Для них не требуется отдельная коллекция.

Доклады пользователя не встраиваются в `users`, потому что доклады являются самостоятельными сущностями, могут участвовать в конференциях и иметь собственный жизненный цикл. Поэтому связь пользователя с докладами реализуется через references из коллекции `talks`.

## Коллекция `talks`

Коллекция `talks` хранит доклады, созданные пользователями.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  title: "Проектирование API для конференции",
  description: "Доклад о проектировании REST API и выборе архитектуры backend-сервиса",
  speaker_id: ObjectId("..."),
  status: "submitted",
  level: "intermediate",
  duration_minutes: 45,
  tags: ["api", "backend", "architecture"],
  materials: [
    {
      type: "slides",
      url: "https://example.com/slides/api-design.pdf"
    },
    {
      type: "repository",
      url: "https://github.com/example/conference-api"
    }
  ],
  created_at: ISODate("2026-05-20T10:30:00Z"),
  updated_at: ISODate("2026-05-20T10:30:00Z")
}
```

### Обоснование модели

Доклад хранится в отдельной коллекции, потому что:

- доклад может существовать независимо от конференции;
- доклад создаётся пользователем;
- один и тот же доклад теоретически может быть связан с разными конференциями;
- по докладам нужно выполнять отдельные CRUD-операции.

Связь с пользователем реализуется через поле `speaker_id`, которое является reference на документ из коллекции `users`.

Поле `materials` встраивается в документ доклада, потому что материалы относятся только к конкретному докладу и обычно читаются вместе с ним.

## Коллекция `conferences`

Коллекция `conferences` хранит конференции и список докладов, добавленных в конференцию.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  title: "System Design Conference 2026",
  description: "Конференция по архитектуре программных систем",
  date: ISODate("2026-06-15T00:00:00Z"),
  location: {
    city: "Москва",
    address: "ул. Примерная, 10",
    online: false
  },
  organizer_id: ObjectId("..."),
  talks: [
    {
      talk_id: ObjectId("..."),
      order: 1,
      room: "Main Hall",
      starts_at: ISODate("2026-06-15T10:00:00Z"),
      status: "accepted"
    },
    {
      talk_id: ObjectId("..."),
      order: 2,
      room: "Main Hall",
      starts_at: ISODate("2026-06-15T11:00:00Z"),
      status: "accepted"
    }
  ],
  tags: ["architecture", "backend", "databases"],
  capacity: 300,
  created_at: ISODate("2026-05-20T11:00:00Z"),
  updated_at: ISODate("2026-05-20T11:00:00Z")
}
```

### Обоснование модели

Конференция хранится в отдельной коллекции, потому что это самостоятельная сущность с собственными CRUD-операциями.

Связь конференции с организатором реализуется через `organizer_id`, который ссылается на документ из коллекции `users`.

Связь конференции с докладами реализована через embedded-массив `talks`, но внутри массива хранятся references на документы из коллекции `talks`.

Такой подход выбран потому что:

- список докладов часто нужен при чтении конференции;
- у связи "конференция — доклад" есть собственные атрибуты: порядок, зал, время начала, статус;
- при этом сам доклад не дублируется полностью, а хранится отдельно;
- обновление названия или описания доклада не требует обновлять все конференции.

То есть используется смешанная модель: embedded document для параметров участия доклада в конкретной конференции и reference для связи с самим докладом.

## Коллекция `tokens`

Коллекция `tokens` хранит токены авторизации пользователей.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  token: "token_abc123",
  user_id: ObjectId("..."),
  created_at: ISODate("2026-05-20T12:00:00Z"),
  expires_at: ISODate("2026-05-21T12:00:00Z"),
  user_agent: "curl/8.0",
  active: true
}
```

### Обоснование модели

Токены можно было бы встроить в документ пользователя, но для данной системы выбрана отдельная коллекция `tokens`.

Причины:

- токены имеют собственный жизненный цикл;
- токены могут истекать и удаляться независимо от пользователя;
- по токену нужно быстро искать пользователя при авторизации;
- пользователь может иметь несколько активных токенов;
- отдельная коллекция позволяет создать индекс по полю `token`.

Связь токена с пользователем реализуется через `user_id`.

## Связи между коллекциями

| Связь | Тип связи | Реализация в MongoDB | Обоснование |
|---|---|---|---|
| User → Talk | 1:N | `talks.speaker_id` reference на `users._id` | Доклады самостоятельны и имеют собственный жизненный цикл |
| User → Conference | 1:N | `conferences.organizer_id` reference на `users._id` | Организатор является отдельной сущностью |
| Conference → Talk | M:N | embedded array `conferences.talks[]` с `talk_id` reference | Нужно хранить параметры доклада внутри конкретной конференции |
| User → Token | 1:N | `tokens.user_id` reference на `users._id` | Токены часто ищутся отдельно и имеют срок действия |

## Где используются embedded documents

Embedded documents используются для данных, которые:

- принадлежат только одному родительскому документу;
- обычно читаются вместе с ним;
- не имеют самостоятельного жизненного цикла.

Примеры:

- `users.contacts`;
- `talks.materials`;
- `conferences.location`;
- элементы массива `conferences.talks`.

## Где используются references

References используются для данных, которые:

- являются самостоятельными сущностями;
- могут часто обновляться независимо;
- используются в разных сценариях;
- могут быть связаны с несколькими другими сущностями.

Примеры:

- `talks.speaker_id`;
- `conferences.organizer_id`;
- `conferences.talks[].talk_id`;
- `tokens.user_id`.

## Индексы

Для эффективной работы API планируются следующие индексы:

```javascript
db.users.createIndex({ login: 1 }, { unique: true })
db.users.createIndex({ role: 1 })
db.users.createIndex({ last_name: 1, first_name: 1 })

db.talks.createIndex({ speaker_id: 1 })
db.talks.createIndex({ title: "text", description: "text" })
db.talks.createIndex({ tags: 1 })

db.conferences.createIndex({ date: 1 })
db.conferences.createIndex({ organizer_id: 1 })
db.conferences.createIndex({ "talks.talk_id": 1 })

db.tokens.createIndex({ token: 1 }, { unique: true })
db.tokens.createIndex({ user_id: 1 })
db.tokens.createIndex({ expires_at: 1 })
```

## Итог

В MongoDB-модели используются четыре коллекции: `users`, `talks`, `conferences` и `tokens`.

Основной принцип проектирования:

- самостоятельные сущности вынесены в отдельные коллекции;
- вложенные данные используются для зависимых объектов;
- связи между крупными сущностями реализованы через references;
- для связи конференций и докладов используется смешанный подход: embedded-документы с reference на доклад.
