# Проектирование кеширования и rate limiting

## Цель

Цель лабораторной работы №5 — оптимизировать производительность REST API сервиса "Сайт конференции" с помощью кеширования и rate limiting.

Система уже содержит API для работы с пользователями, докладами и конференциями. В рамках данной лабораторной работы анализируются hot paths, выбираются стратегии кеширования, описываются правила инвалидации кеша и проектируется ограничение частоты запросов.

## Анализ производительности

### Часто выполняемые операции

К часто выполняемым операциям относятся:

1. `GET /talks` — получение списка всех докладов.
2. `GET /conferences/{conferenceId}/talks` — получение списка докладов конкретной конференции.
3. `GET /users/search` — поиск пользователей по имени и фамилии.
4. `GET /users/by-login` — поиск пользователя по логину.
5. `POST /auth/login` — вход пользователя в систему.
6. `GET /mongo/users` — получение статистики по пользователям MongoDB.

### Потенциально медленные операции

Потенциально медленными являются операции, которые обращаются к базе данных:

- чтение списка всех докладов из PostgreSQL;
- чтение списка докладов конференции из PostgreSQL;
- поиск пользователей по маске имени и фамилии;
- проверка логина и пароля при авторизации;
- подсчёт статистики пользователей в MongoDB;
- запросы, использующие соединения между таблицами;
- запросы, возвращающие большие списки данных.

### Hot paths

В качестве hot paths для оптимизации выбраны:

| Endpoint | Причина |
|---|---|
| `GET /talks` | Часто вызывается пользователями для просмотра программы и списка докладов |
| `GET /conferences/{conferenceId}/talks` | Часто вызывается при открытии страницы конкретной конференции |
| `POST /auth/login` | Чувствительный endpoint, который может быть целью brute-force атак |

## Требования к производительности

Для учебного проекта принимаются следующие целевые требования:

| Операция | Целевое время ответа |
|---|---:|
| Чтение из кеша | до 50 мс |
| Чтение из PostgreSQL | до 200 мс |
| Создание или обновление данных | до 300 мс |
| Проверка rate limit | до 10 мс |

Также предполагается:

- API должен корректно отвечать при повторяющихся запросах;
- кеш должен снижать количество обращений к БД;
- изменение данных должно инвалидировать устаревший кеш;
- rate limiting должен защищать чувствительные endpoints от слишком частых запросов.

## Стратегия кеширования

### Выбранные endpoints

Кеширование применяется минимум для двух endpoints:

1. `GET /talks`
2. `GET /conferences/{conferenceId}/talks`

Эти endpoints выбраны потому что они:

- часто читаются;
- не изменяют состояние системы;
- возвращают данные, которые обычно не меняются каждую секунду;
- могут создавать лишнюю нагрузку на PostgreSQL при большом количестве пользователей.

### Endpoint `GET /talks`

Назначение: получение списка всех докладов.

Стратегия кеширования:

- Cache-Aside;
- ключ кеша: `talks:all`;
- TTL: 60 секунд;
- инвалидация: при создании нового доклада через `POST /talks`.

Обоснование:

Список докладов часто читается пользователями. При этом новые доклады создаются значительно реже, чем читается список. Поэтому кеширование списка докладов уменьшает количество запросов к PostgreSQL.

### Endpoint `GET /conferences/{conferenceId}/talks`

Назначение: получение списка докладов конкретной конференции.

Стратегия кеширования:

- Cache-Aside;
- ключ кеша: `conference:{conferenceId}:talks`;
- TTL: 60 секунд;
- инвалидация: при добавлении доклада в конференцию через `POST /conferences/{conferenceId}/talks/{talkId}`.

Обоснование:

Страница конференции может часто открываться участниками. Список докладов конференции обычно меняется только при действиях организатора, поэтому его можно безопасно кешировать на короткое время.

## Выбор стратегии Cache-Aside

Для обоих endpoints используется стратегия Cache-Aside.

Алгоритм:

1. API получает GET-запрос.
2. API проверяет наличие значения в кеше.
3. Если значение найдено, API возвращает ответ из кеша.
4. Если значения нет, API выполняет запрос к PostgreSQL.
5. Результат сохраняется в кеше с TTL.
6. API возвращает результат клиенту.

Преимущества:

- простая реализация;
- кеш используется только для часто читаемых данных;
- при ошибке кеша можно продолжить работу через базу данных;
- легко реализовать инвалидацию по ключу.

Недостатки:

- первый запрос после истечения TTL всё равно обращается к БД;
- возможна кратковременная отдача устаревших данных до инвалидации или истечения TTL.

## Инвалидация кеша

Для предотвращения отдачи устаревших данных используется явная инвалидация кеша.

| Операция | Инвалидируемый ключ |
|---|---|
| `POST /talks` | `talks:all` |
| `POST /conferences/{conferenceId}/talks/{talkId}` | `conference:{conferenceId}:talks` |

Дополнительно TTL ограничивает время жизни данных в кеше.

## TTL

Для учебного проекта выбран TTL 60 секунд.

Обоснование:

- данные достаточно быстро обновляются после изменений;
- при отсутствии явной инвалидации устаревшие данные живут недолго;
- TTL достаточно большой, чтобы снизить нагрузку при частых повторных запросах;
- TTL достаточно маленький, чтобы не ухудшать пользовательский опыт.

## Rate limiting

### Цель

Rate limiting нужен для защиты API от чрезмерного количества запросов.

Основные цели:

- защита от brute-force атак на login endpoint;
- снижение нагрузки на backend;
- предотвращение злоупотребления API;
- стабилизация времени ответа под нагрузкой.

### Endpoint для rate limiting

Rate limiting применяется к endpoint:

```text
POST /auth/login
```

Обоснование:

- endpoint чувствителен к brute-force атакам;
- частые неуспешные попытки входа создают нагрузку на PostgreSQL;
- ограничение количества запросов повышает безопасность системы.

## Алгоритм rate limiting

Для реализации выбран алгоритм Fixed Window Counter.

Параметры:

- окно: 60 секунд;
- лимит: 5 запросов на клиента в рамках одного окна;
- идентификатор клиента: IP-адрес;
- при превышении лимита возвращается HTTP `429 Too Many Requests`.

### Обоснование выбора Fixed Window Counter

Преимущества:

- простая реализация;
- низкие накладные расходы;
- подходит для учебного проекта;
- легко тестируется;
- достаточно эффективен для ограничения login endpoint.

Недостатки:

- возможны всплески запросов на границе временных окон;
- для распределённой системы потребовалось бы хранить счётчики во внешнем хранилище, например Redis.

Для текущего учебного проекта in-memory реализация считается достаточной, так как приложение запускается в одном экземпляре.

## Заголовки rate limiting

При каждом запросе к защищённому endpoint API добавляет заголовки:

| Заголовок | Значение |
|---|---|
| `X-RateLimit-Limit` | максимальное количество запросов в окне |
| `X-RateLimit-Remaining` | оставшееся количество запросов |
| `X-RateLimit-Reset` | Unix timestamp окончания текущего окна |

Если лимит превышен, API возвращает:

```text
HTTP/1.1 429 Too Many Requests
```

И JSON-ответ:

```json
{
  "error": "rate limit exceeded"
}
```

## Метрики производительности

Для оценки эффективности кеширования и rate limiting можно использовать следующие метрики:

### Метрики кеширования

| Метрика | Описание |
|---|---|
| Cache Hit Count | количество успешных чтений из кеша |
| Cache Miss Count | количество промахов кеша |
| Cache Hit Rate | доля запросов, обслуженных из кеша |
| Cache Evictions | количество удалений из кеша |
| Cache TTL Expiration | количество истечений TTL |

Формула hit rate:

```text
hit_rate = cache_hits / (cache_hits + cache_misses)
```

### Метрики API

| Метрика | Описание |
|---|---|
| Response Time | время ответа endpoint |
| Requests Per Second | количество запросов в секунду |
| Error Rate | доля ошибочных ответов |
| 429 Count | количество ответов Too Many Requests |
| DB Queries Count | количество обращений к базе данных |

### Метрики PostgreSQL

| Метрика | Описание |
|---|---|
| Query Time | время выполнения SQL-запросов |
| Active Connections | количество активных соединений |
| Slow Queries | количество медленных запросов |

## Ожидаемый эффект

Кеширование должно снизить количество повторных обращений к PostgreSQL для часто читаемых endpoints.

Ожидаемый эффект для `GET /talks`:

- первый запрос читает данные из PostgreSQL;
- последующие запросы в течение TTL читают данные из кеша;
- после `POST /talks` кеш инвалидируется.

Ожидаемый эффект для `GET /conferences/{conferenceId}/talks`:

- первый запрос читает данные из PostgreSQL;
- повторные запросы читают данные из кеша;
- после добавления доклада в конференцию кеш конференции инвалидируется.

Rate limiting должен ограничить частоту запросов к `POST /auth/login` и возвращать `429 Too Many Requests` при превышении лимита.

## Итоговая стратегия

В лабораторной работе реализуется:

1. Cache-Aside кеширование для:
   - `GET /talks`;
   - `GET /conferences/{conferenceId}/talks`.

2. Инвалидация кеша при изменении данных:
   - `POST /talks`;
   - `POST /conferences/{conferenceId}/talks/{talkId}`.

3. Fixed Window Counter rate limiting для:
   - `POST /auth/login`.

4. Документирование:
   - hot paths;
   - медленных операций;
   - TTL;
   - стратегии инвалидации;
   - алгоритма rate limiting;
   - метрик производительности.
